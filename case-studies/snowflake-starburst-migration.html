Snowflake to Starburst + Iceberg migration

When BILL acquired Divvy, the data-platform integration had to consolidate analytics workloads without interrupting financial reporting. We moved workloads from Snowflake into BILL’s Starburst/Trino and Apache Iceberg lakehouse, with evidence for Sarbanes-Oxley (SOX) controls built into every migration batch. The old and new paths ran in parallel until per-object checks passed, consumers were repointed, and accountable owners approved cutover.

Method

The migration, step by step

Step 1: define the control boundary

This was an acquisition integration, not a simple platform swap. The first deliverable was an object inventory with one accountable role, one target pattern, and one acceptance state per workload. The inventory kept migration progress, consumer readiness, and control evidence in the same view.

A generic migration record 
object_ref: reporting_object
source_platform: snowflake
target_platform: iceberg
migration_pattern: rebuild_in_dbt
accountable_role: data_product_owner
required_checks:
  - availability
  - schema_shape
  - row_count
  - data_composition
cutover_gates:
  - checks_passed
  - consumers_repointed
  - owner_approved

Step 2: run both paths during transition

Snowflake remained the comparison point while Starburst/Trino read the new Apache Iceberg data. This parallel period separated data movement from consumer cutover: engineers could prove parity first, then move dashboards and scheduled workloads in controlled batches.

Step 3: choose a migration pattern per object

Stable data could be copied once and checked. Maintained transformation logic moved into dbt. Historical snapshots preserved their effective-date behavior. Unused or invalid objects went through a documented removal path instead of being copied automatically. Treating the inventory as a decision queue prevented legacy clutter from becoming lakehouse clutter.

Decision logic used by the migration queue 
if object_is_unused_or_invalid:
    route = "review_then_remove"
elif object_contains_maintained_logic:
    route = "rebuild_in_dbt"
elif object_preserves_history:
    route = "copy_with_history_checks"
else:
    route = "copy_then_validate"

publish(route, owner_role, required_checks)

Step 4: make parity the acceptance evidence

Availability alone was not enough. The check compared object presence, schema shape, row counts, and composition signals such as date ranges, numeric totals, key uniqueness, boolean distributions, and null rates. Results were attached to the migration record, which made the same evidence useful for engineering review and SOX control support.

Per-object parity contract 
checks = [
    compare_availability(legacy_object, lakehouse_object),
    compare_schema_shape(legacy_object, lakehouse_object),
    compare_row_count(legacy_object, lakehouse_object),
    compare_data_composition(legacy_object, lakehouse_object),
]

result = "pass" if all(check.passed for check in checks) else "review"
publish_evidence(object_ref, result, checks)

Step 5: repoint consumers without a single cutover event

Tableau data sources and scheduled consumers moved by owner and workload group. A compatibility path kept reads available while connections changed. Each group had a short acceptance loop: repoint, compare, confirm, and monitor. This reduced cutover risk and gave users clear ownership for questions and incidents.

Step 6: operate Iceberg as a storage system

The migration initially created an Apache Iceberg footprint about three times larger than expected. The response combined small-file compaction, snapshot expiry, orphan-file cleanup, and manifest maintenance, all protected by a row-count guard. The durable lesson was operational: moving data to object storage does not remove storage management; it changes which maintenance controls matter.

Maintenance order with a safety gate 
before = capture_row_count(table_ref)

compact_small_files(table_ref)
expire_snapshots(table_ref, retention_policy)
remove_orphan_files(table_ref, retention_policy)
rewrite_manifests(table_ref)

after = capture_row_count(table_ref)
assert after == before

Results

What the integration delivered

The measured checkpoint showed that the architecture and operating model were working together: progress was visible, acceptance was evidence-based, and the financial benefit could be tied to retirement of the separate platform.
